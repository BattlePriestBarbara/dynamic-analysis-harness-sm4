# 12 经验与教训

> 这一章比结论更耐用。它记录的是**怎么被骗**，以及**怎么发现被骗**。

## 12.1 三次"看起来对"的误判

### 误判 1：把"367,228 字节"当成"一次连续解密"

- **当时**：对比文件与镜像，找到一段最大连续变更区间 367,228 B，写成"壳一次性解密了 367 KB"。
- **后来**：改成全量集合差分 → **509,935 B / 8,675 段**，且分成两类效应
  （352,046 就地解密 + 157,889 解包写入 RW）。
- **根因**：用"最大连续区间"代表"变更总量"。这两个量在**分段写入**的场景下毫无关系。
- **修法**：差分永远先算**全量集合**，再按位置/类型分类；不要用连续区间做摘要。

### 误判 2：把 737 项缺口当成"保护名单"

- **当时**：发现索引少了 737 个条目，且缺口里包含敏感资源，于是写成"这些资源被标记保护"，
  并据此判定"补记录（路线 A）不可行"——这是一个**极性错误**。
- **后来**：`omitted == {header_offset < 0x511c9c4}` 精确成立（737/737，delta 直方图 `[(0,737)]`）→
  缺口是**连续的偏移前缀**，不是策略集合。路线 A 反而成了唯一可行解。
- **根因**：**先有叙事，再看数据**。"保护名单"是个好听的故事，而"游标起点"听起来像 bug。
- **修法**：任何"某某被挑选/被保护"的结论，先问：
  **这个集合能不能写成一个连续数值条件？** 能，就几乎肯定不是策略。

> **⚠ 这一条后来又被翻了第二次。** "缺口是连续的偏移前缀"是对的，但它的原因既不是策略、
> 也不是壳的游标起点，而是**本仓库 harness 的清零 hook 在索引构建中途抹掉了前 737 条插入**
> （[08 §8.13](08-APK内部索引缺口.md)）。所以"路线 A 是唯一可行解"这句话也一起作废——
> 根本不需要补记录，重跑一次就有完整索引。
>
> 教训升级为：**"连续数值条件"能排除"策略"，但不能证明"是壳的行为"**。
> 排除掉一种解释之后，还要问一句"这组数字会不会是我的观测方式产生的"。

### 误判 3：把 `0x120f42f0` 当成 CFF 状态表基址

- **当时**：工具在该地址读到 256 项、全部落在镜像内，于是判定"表找到了"。
- **后来**：发现它没有任何 `adrp+add` 引用，且恰好 = `0x120f3af0 + 256×8`（**越过末尾一格**）。
  真正的基址由 `adrp/add` 在 `+0xbd74c`/`+0xbd750` 处构造。
- **根因**：把"数据长得像表"当成了"这就是表"。**指针全在镜像内从来不是充分证据**——
  因为镜像本身就是一段连续指针区（`0x120f3a50..0x120f51c8` 有 751 个 qword）。
- **修法**：任何"表基址"必须由**代码引用**确定，而不是由"读出来的值合理"确定。

## 12.2 五个工程坑

| # | 坑 | 表现 | 处置 |
|---:|---|---|---|
| 1 | 非 ASCII 用户名破坏 classpath | `NoClassDefFoundError`，jar 明明在 | classpath 写进 `cp.txt` 用 `@cp.txt`；或换 ASCII 路径 |
| 2 | 调试器在异常时阻塞 | "卡死"，无输出 | 重定向 stdin（给 EOF）；先分清"挂住"和"失败" |
| 3 | Python 版本分裂 | "包不存在"，其实装在了另一个解释器 | 显式 `py -3.12`；台账记录解释器与包版本 |
| 4 | 抓取文件覆盖式打开 | 某次运行没到 `setkey`，把上次已验证的密钥**擦成空文件** | `keep` 旗标：先改名 `.bak` 再截断（默认关，保历史可比） |
| 5 | 基于 capstone 的脚本无法运行 | 脚本写完才发现**只有 unidbg 的 native 侧有 capstone**，Python 侧没有 | 改用 Ghidra 路线（已可用）；或在正确的解释器里装包后重跑 |

> 坑 5 的教训最具体：**"我知道有这个库"不等于"这个环境有这个库"**。
> 写脚本前先 `python -c "import capstone"` 一行验证，能省一下午。

## 12.3 三个环境层面的坑

1. **Frida MCP 的 `usb` 选择器在双 transport 环境下会选错** → 显式用 `127.0.0.1:27042`。
2. **`lief` 在 10 MB 级 so 上枚举符号会卡死** → 自写 `elf_scan.py`（136 个库 2.2 秒）。
3. **重打包工具会"顺手"删掉 `META-INF`** → `apksigner` 即使关闭 v1 签名，也会删除
   `MANIFEST.MF / *.SF / *.RSA`（实测签名后该目录为空），导致"保留原始签名"实验直接不可行。

## 12.4 四条方法论

### (1) 用两条互不依赖的路径证同一件事

ZIP 结构用了两条：**相信中央目录的覆盖法**（5,161/5,161 全部 `PK\x03\x04`，漂移 0）
与**不信中央目录的裸走查法**（232,579,361 B 全扫，5,162 命中 / 5,161 个唯一名）。
两条独立路径的**差值**就是假阳性，也正是最值得看的地方。

### (2) 控制运行（control run）必须保留

把工具指向**已知错误**的输入（错误基址），看它是否仍然"给出漂亮结果"。
如果它照样 256/256、照样"全部在镜像内"，那就证明**这个判据本身无效**。
错误输出不删，与正确输出并列保存。

### (3) 否定性结论优先写

"这里**没有** VMP ISA"、"`IJMDal.Data` 里**没有**明文"、"索引**不是**保护名单"——
这三条省下的工作量远超它们的花费。**证伪比证明更省钱。**

### (4) 把"运行期偶然"升级成"可重复的单元测试"

SM4 那条链之所以可信，不是因为"某次跑通了"，而是因为：
`-D…sm4selftestOnly=true` 能把整条密码学路径从 JNI 里**独立出来跑**，
并与**独立参考实现**逐字节比对。任何"只跑通过一次"的观测都不算证据。

## 12.5 如果重来一次，会怎么排

| 顺序 | 动作 | 理由 |
|---:|---|---|
| 1 | 先做**结构盘点**（体积、组件、so、容器熵） | 半小时内知道"该不该投入" |
| 2 | 先读 `DT_HASH`，不信节头 | 少浪费一整轮 Ghidra |
| 3 | **跳过设备路线**，直接上仿真器 | 设备路线已被证明封死（v1 逐条目摘要 + 裸 syscall） |
| 4 | 仿真器先跑**初始化 + dump 镜像**，再谈别的 | 镜像是后续一切静态分析的前提 |
| 5 | 从**隐藏注册表**出发找目标函数，而不是从字符串出发 | `register_natives.tsv` 是确定的入口 |
| 6 | 密码学部分**先写独立参考实现**，再比对 | 避免"两个错误互相掩盖"（见 [07 §7.5](07-SM4链路逐跳定位.md)） |
| 7 | 索引/格式类问题**先做集合等式**，再谈机制 | 一个等式能杀掉三个解释 |
