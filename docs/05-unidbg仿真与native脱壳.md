# 05 unidbg 仿真与 native 脱壳

## 5.1 为什么 unidbg 可行

设备路线的失败点在"完整性校验先于解密"。而 unidbg 的思路正好相反：

- 它**不做任何校验**——它只是把 `libexec.so` 按 ELF 加载、把 `DT_INIT` 跑一遍；
- 它**不模拟 ART**，因此壳里依赖 Java 环境的部分会失败——但**解密发生在依赖 Java 之前**；
- 它**可观测**：每次内存映射、读写、syscall 都能记账。

一句话：**仿真器不是"更弱的真机"，而是"能跳过前置校验的显微镜"。**

## 5.2 工程结构

```
<UNIDBG>/
└── src/<harness>/Emulator.java      6,549 行
    ├── 加载：ELF 段映射 + 补 AAssetManager_* 等导入
    ├── 初始化：setCallInitFunction(false) + 反射调用 DT_INIT
    ├── 观测：内存写钩子 / syscall 钩子 / RegisterNatives 钩子

    └── 开关：-D<prefix>.* 共 12 项（见 §5.7）
```

## 5.3 SMC：一个 mmap/munmap 账本问题

`DT_INIT` 的第一件事是**在自己的镜像上重映射**：

```
mmap(MAP_FIXED, base + 0x40000, 0xafff0)
```

unidbg 只跟踪真实 ELF 段，所以随后那个 `munmap` 抛出：

```
IllegalStateException: munmap aligned=0xb0000, start=0x12040000
```

**修法（三步，缺一不可）**：

1. `setCallInitFunction(false)` —— 不让 unidbg 自己调 init，改由我们控制时机；
2. `coverModuleSpan()` —— 把 `memoryMap` 账本里的条目**扩到整个镜像跨度**（`0x11c000`）；
3. 反射调用 `LinuxModule.callInitFunction` —— 在账本已修正后执行 `DT_INIT`。

> 这不是"绕过 unidbg 的限制"，而是**修正它对 SMC 的建模缺陷**：
> 一个会重映射自身镜像的库，要求 loader 的记账粒度是"整镜像"而不是"段"。

**独立校验**：`spanFromElf()` 重算出的跨度 = `0x11c000` = 镜像大小，**逐字节相等**。
这条等式同时验证了"loader 模型对"和"dump 完整"。

## 5.4 差分结果：509,935 字节不是"一次连续解密"

把磁盘文件与初始化后的镜像逐字节比对：

| 指标 | 值 |
|---|---|
| 变更字节总数 | **509,935** |
| 变更段数 | **8,675** |

按位置分类：

| 效应 | 字节 | 位置 |
|---|---:|---|
| **就地解密** | **352,046** | `< 0x98c84`（`PT_LOAD[0]`，壳保护的代码段） |
| **解包写入 RW** | **157,889** | `>= 0x98c84`（`PT_LOAD[1]`） |

**这是一次修正**：早期报告写的"367,228 B 一次连续解密"是错的——它只统计了连续区间，忽略了尾部。
`157,889` B 的尾部不是噪声，它是壳往 RW 段解包出来的东西（数据 / 跳板 / 注册表）。

> 教训：**"最大连续变更区间"不是"变更总量"**。差分要按"全量集合"统计，再按位置分类，
> 否则会把一个双效应过程误读成单效应过程。

## 5.5 产物与 11 个隐藏注册

| 产物 | 大小 | 说明 |
|---|---:|---|
| `libexec_image.bin` | 1,163,264 | **权威**：`DT_INIT` 之后的完整内存镜像，基址 `0x12000000` |
| `libexec_dumped.so` | 791,584 | 同一批字节回填进一个可加载 ELF（`ehdr`/`phdrs`/`shdrs` 与原文件一致） |
| `register_natives.tsv` | 914 | **11 个隐藏注册**，含精确偏移（sha256 `7f1cd27fd6089510…`） |
| `dex_*.dex`（156 B） | 156 | **诱饵**：`version=035, class_defs=0`，仅用于负向测试 |

11 个注册是这轮最有用的副产品：它把"壳暴露给 Java 的 native 方法"从**不可见的符号表**
变成了**一张确定的表**——后续所有 hook / 仿真调用都从这张表出发，而不是从猜地址出发。

## 5.6 两堵墙（为什么一期到此为止）

### 墙 1：没有 ART，所以抓不到 DEX

壳的 `N.l / N.r / N.ra` 最终会把 DEX 以 `byte[]` 交给 `ClassLoader`。
unidbg **不实现 ART**，所以这条链在 Java 侧断掉——native 解密可能成功了，但没有"接收方"。

- 不是参数没调对，而是**模型里缺一个组件**。
- 想补：需要自己实现 `BaseDexClassLoader.addDexPath` / `InMemoryDexClassLoader` 的行为，
  等于写半个 ART。**投入产出比不成立。**

### 墙 2：`AAssetManager_*` 是导入，不是实现

| 符号 | 状态 |
|---|---|
| `AAssetManager_open` / `read` / `getLength` / `close` | **导入**（`st_value = 0`），unidbg 无实现 |

壳读加密资产全靠这套 API。unidbg 里它们未解析，于是"读资产"这一步直接失败。

- 可以补桩（返回我们自己准备的数据），本轮也做了部分；
- 但补桩之后**下游仍然卡在墙 1**——DEX 无处可去。

> 两堵墙的顺序很重要：**先撞墙 2，补完才发现墙 1 才是真墙**。
> 如果一开始就知道"没有 ART"，就不会在 `AAssetManager` 上花那么多时间。

## 5.7 一期的开关（可复现性的一部分）

`<harness>.Emulator` 有 12 个 `-D` 开关，其中三个直接影响结论：

| 开关 | 默认 | 作用 |
|---|---|---|
| `-D<prefix>.sm4selftestOnly=true` | false | 只跑 SM4 自测（初始化后立刻退出），用于隔离验证 |
| `-D<prefix>.sm4dyn.keep=true` | **false** | 抓取前把旧文件重命名为 `name.<epochMillis>.bak`，而不是直接截断 |
| `-D<prefix>.wlBypass=off\|all` | on（仅两个名字） | 关闭 / 放开资产索引旁路，用于"纯观测"对照 |

**`keep` 旗标解决的是一个真实事故**：抓取文件每次 `hookSm4Dynamic()` 都以覆盖模式打开，
于是"某次运行没走到 `setkey`"就会**擦掉上一次已校验的密钥**。默认关（保持历史可比），
需要时显式打开。

> 到本文档为止，`keep` 只做了**编译验证**，未做运行时确认 → 记入 [00 §0.3 第 15 行](00-摘要与结论分级.md) 的待办。

## 5.8 一期结论

> 拿到了该拿的（解密镜像 + 11 个隐藏注册 + 完整可观测的执行记录），
> 拿不到想要的（DEX）。
> **一期的价值不在"脱壳成功"，而在"把壳变成可观测对象"**——没有这一步，
> 后面的 SM4 逐跳定位（[07](07-SM4链路逐跳定位.md)）根本无从下手。
