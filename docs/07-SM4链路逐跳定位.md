# 07 SM4 链路逐跳定位

这一章是整份报告里**证据最密**的一段：每一跳都有地址、指令和运行期数值。
它也是唯一一条"从 JNI 一路走到密码学原语"的完整链路。

## 7.1 起点：为什么盯住 `N->l`

壳暴露给 Java 的 native 方法里，`N->l` 是被业务层真正调用的那个（[05 §5.5](05-unidbg仿真与native脱壳.md) 的 11 个注册）。
从它往回看调用链，落点在：

```
0x120740e0  →  0x12073538（wrapper）  →  0x1204f2a0（block loop）  →  0x1204edd8（key schedule）
```

## 7.2 wrapper `0x12073538` 的控制流（实测）

```
0x120735cc  bl   0x12073180            ; 资产存在性闸门：返 0 则继续
0x1207360c  ldrb w9,[self+0x1df]       ; 选择 reader（两条实现分支）
0x12073680  blr  x9                    ; reader A: fn(self->[0x80], name, &ptr, &len)
0x120736b0  blr  x9                    ; reader B: 6 参数变体
0x12073758  snprintf(sp+0x160, "%scom.ijiami.vcPathList", apkPath)
0x12073778  stp  q0,q0,[x21]           ; 清空 key 暂存缓冲
0x1207379c  blr  x22                   ; 配置查询 → 写 x21
0x120737c8  key = x21[6..22] XOR image[0x12103564 ..]
0x120737f4  len = [sp+8]; src = [sp+0x10]
0x1207380c  bl   0x1204f2a0            ; 就地解密
```

三个结论：

1. **key 不是硬编码常量**，而是"配置值前 16 字节 XOR 镜像里的一段表"——
   即**密钥被拆成两半，一半在 APK 配置里、一半在 native 镜像里**。
2. 配置键由 `apkPath + "com.ijiami.vcPathList"` 拼成，**路径参与键名** →
   换路径（重打包 / 换安装位置）会改变键名 → 取不到值。这是**反重打包**的另一种形式。
3. reader 有两条实现，由 `self+0x1df` 的字节选择——同一份代码里有**两条取数路径**。

## 7.3 字符串是"替换表"解出来的

wrapper 里的字符串不是明文，也不是简单 XOR。解码循环做的是**两次 `ldrb`**：

```
str[k] = B[ A[ i ] ]
```

即**双表替换**。用 `_diag_wrapper_strings.py` 解出三条：

| 长度 | 字符串 | 角色 |
|---:|---|---|
| 16 | `sign_verify.png` | `0x12073180` 闸门的键 |
| 22 | `assets/sign_verify.png` | 交给 reader 的名字 |
| 23 | `%scom.ijiami.vcPathList` | 配置键的格式串 |

> 这里有一个方法论要点：**看到 `ldrb` 两次就不能假设 XOR**。
> 早期把它当 XOR 试，得到的是一堆不可读字节；改成"双表查表"后一次就对。

## 7.4 key 的来源：32 字符十六进制串

运行期在 `setkey` 处捕获到 16 字节密钥（**已脱敏**）：

```
c38c68b0********…       ← 完整值仅保留在本地证据
```

同时捕获到配置侧暂存缓冲的前若干字节（十六进制字符串形式），
两者按 §7.2 的 XOR 关系得到上面的 16 字节。

## 7.5 `setkey` 与轮密钥方向

`0x1204eec4` 就是 `setkey(ctx, key)`（`x0 = ctx`，`x1` = 16 字节密钥）：

```
0x1204eed0  mov  w8, #1
0x1204eed4  mov  x19, x0
0x1204eed8  str  w8,[x0],#8      ; ctx[0] = 1 (mode)，随后 x0 = ctx+8
0x1204eedc  bl   0x1204edd8      ; 密钥编排跑在 ctx+8 上
```

密钥编排是**教科书式 GB/T 32907-2016**：

| 要素 | 值 |
|---|---|
| 大端密钥字 | `lsl` / `rev` 组合 |
| FK | `a3b1bac6 / 56aa3350 / 677d9197 / b27022dc` |
| CK 表 | 偏移 `0x12027610`，**与标准逐字节一致** |
| S-box | 偏移 `0x12027710` |
| 循环移位 | `rol13` / `rol23` 用 `bfi` 构造 |

**关键偏差**：`0x1204eee0..0x1204ef9c` 用 `ext #8` 做 16 字节块交换级联，
把 32 项**整体反转**。所以布局是：

```
ctx + 8 + 8i  ==  rk_std[31 - i]
```

验证：`_verify_sm4c.py` → **reversed: 32/32**；按正序比对 → **0/32**。
两个数字一起构成证明：**只有"反转"这一种解释能同时满足 32 个位置**。

> 早期的第一版校验脚本报 0/32，原因是双重的：既按正序比对，`T'` 又用了
> `b << 13` 而不是 `rol(b,13)`。**两个独立错误互相掩盖**，是本次最典型的一次"看起来像结论"。

## 7.6 `block_loop`：in-place 解密 + 不校验的填充

`0x1204f2a0` 的签名是 `block_loop(ctx, len, src, dst, outlen)`，调用时 **`dst == src`**（就地）。

- 按存储的**反转后**的轮密钥**正序走**，等价于**SM4 解密**；
- 不做 PKCS#7 校验，直接剥离尾部 → 调用方**无法感知解密是否正确**。

> 这条事实很重要：它解释了为什么后面"解出来看着不像明文"却不报错——
> **解密链本身不提供正确性信号**，必须自己用别的手段判定。

## 7.7 约定判定：`dec_BEwords`，80/80

把真实输入（`assets/<blob>`，80 字节）喂给 guest，再用独立参考实现按四种约定各算一遍：

```
guest         0f88581b33aac179…
dec_BEwords   0f88581b33aac179…   MATCH
enc_BEwords   14af47b4…          (方向相反，不是它)
```

**80/80 字节完全一致**。因此：

> wrapper 收到的是**密文**，产出的是**明文**。
> 把这条路径称作"加密资产"是错的——它是**解密**。

这个判定同时排除了"小端 / 加密方向"等其他三种解释：它们都在第一个 block 就分叉。

## 7.8 自测：把整条密码学路径从 JNI 里独立出来

为了让这条结论不依赖"某次运行恰好走到"，加了自测模式：

```
-D<prefix>.sm4selftestOnly=true     # 初始化后立刻跑自测并退出
```

自测内容：用捕获的密钥 + 真实 80 字节输入，调 guest 的 `0x1204f2a0`，
与独立参考实现的 `dec_BEwords` 比对。

- 日志输出 `[SM4-SELFTEST] MATCH`；
- 产物 `sm4_guest_actual.bin` 与 `sm4_guest_expected.bin` **逐字节相同**。

> 这一步把"运行期偶然观测"升级成"**可重复的单元测试**"，
> 是整份报告里最值得抄的做法。

## 7.9 动态捕获：把每个阶段写成文件

| 捕获文件 | 内容 |
|---|---|
| `sm4_key_dynamic.bin` | 16 B，`setkey` 时的密钥 |
| `sm4_roundkeys_dynamic.bin` | 272 B，32 × 8 轮密钥 + 头 |
| `sm4_io_dynamic.jsonl` / `.bin` | 每次 `block_loop` 的入参/出参见证 |
| `sm4_loop_dynamic.bin` | 循环内部状态（用于比对约定） |
| `wrapper_callsite.jsonl` | wrapper 的关键寄存器与字符串（路径、暂存缓冲） |

**一个真实事故**：这些文件以覆盖模式打开，某次运行没走到 `setkey`，
就把上一次已校验的密钥**擦掉了**。修法见 [05 §5.7](05-unidbg仿真与native脱壳.md)（`keep` 旗标）。

## 7.10 闸门、reader 与 APK 内部索引

`0x12073180` 是**资产存在性闸门**：返回 0 则继续，非 0 则跳过整条解密。
它查的不是文件系统，而是 **APK 内部索引**——这就是 [08](08-APK内部索引缺口.md) 的入口。

对照实验证明了下游是通的：

```
旁路闸门（默认，仅两个名字） → wrapper 继续 → reader 取数 → 解密执行 → 有输出
强制指定索引内的名字        → 同样跑通 → 说明 reader / 解密 / 输出全链路无问题
```

**所以阻塞点唯一地落在"索引不列这个名字"上**，而不是密码学。

> **⚠ 这句在 §7.12 之后要改口径**：阻塞点当时确实在"索引不列这个名字"，
> 但那个"不列"是**本仓库 harness 的清零 bug** 造成的（见 [08 §8.13](08-APK内部索引缺口.md)），
> 不是壳的行为。修掉之后闸门直接放行，链路一次跑通。

## 7.12 索引修好之后：密钥、blob 与"填充不成立"的终局

### 7.12.1 链路第一次真正执行

修掉 [08 §8.13](08-APK内部索引缺口.md) 那个"构建中途清零哈希表"的 harness bug 之后，
同一份 APK、同一个 harness，日志变成：

```text
[WHITELIST] verdict key="assets/sign_verify.png" lookup=0x3f7a -> present (not forced)
[READER] 4-arg returned 0x1 data=0x1283b000 len=80 head=746db8cf…
[SM4-DYN] setkey #2 … key16=c38c68b0…
[SM4-DYN] block_loop #2 len=80(0x50) … in=746db8cf…
```

对照修复前：`setkey=0 / block_loop=0`（链路根本没进）。
修复后：`setkey=2 / block_loop=2 / blocks=7`。

⇒ **第 13 号悬案有答案了**：那把 16 字节密钥，在这一轮里被用来解
`assets/sign_verify.png`（80 B = 5 个 block）。

### 7.12.2 但解出来的不是合法明文，而且 guest 自己也不认

用独立参考实现（guest 自己的 S-box / CK 表）把四种约定都算一遍：

| 解释 | 与 guest 是否一致 | PKCS#7 | 末字节 |
|---|---|---|---|
| ECB + **反转**轮密钥（guest 约定） | **逐块一致**（blk0 = `0f88581b33aac179…`） | ✗ | `0x6d` |
| ECB + 标准轮密钥顺序 | 方向相反，不是它 | ✗ | `0xb4` |
| CBC，IV = 全 0 | — | ✗ | `0x79` |
| CBC，IV = 第 0 块 | — | ✗ | `0x79` |

而且壳自己算出来的结论也是"失败"：

```text
[SM4-DYN] block_loop #2 done len=80 outlen=-29 pad=109
```

`pad=109` 就是末字节 `0x6d`（`'m'`）。壳按"末字节即填充长度"的老写法得到 `80 − 109 = −29`，
于是把这次解密判为失败并放弃。

同一把密钥去解另一个 32 B 资产 `assets/icon/image_icon_constructor_encrypted.png`
同样不成立（末字节 `0x5e`）——**两处独立命中、两处同样失败**，说明这不是某个 blob 的偶然。

### 7.12.3 #13 / #14 的准确表述

| # | 问题 | 现在的回答 |
|---|---|---|
| 13 | 密钥解的是哪个 blob | **已证**：`assets/sign_verify.png`（80 B），另加一个 32 B 的 icon 资产 |
| 14 | 那 80 字节是密文还是签名块 | **仍未定**，但可选空间已被压窄到两条：<br>① 它是密文，但**不是用这把密钥**加密的（密钥另有所指）；<br>② 它根本不是 SM4 数据，只是被顺手喂了一次 `block_loop`，失败即放弃 |

> 一条方法论在这里又被验证了一次（[§7.6](#76-block_loopin-place-解密--不校验的填充)）：
> **`block_loop` 不校验填充，所以"跑通了"不等于"解对了"**。
> 唯一能判对错的，是独立实现 + 填充/结构检查；只看"有没有输出"会得到反向结论。

### 7.12.4 下一刀切在哪：一个可证伪的假设

这次调用前后，wrapper 还碰了两样东西，日志里都留了痕：

```text
sp+0x148  "%scom.ijiami.vcPathList"                      ← 命名空间/清单字符串
[HP]      digest input … ascii="data/app/<pkg>-1/base.apk_IJM_2019…"
          remaining 55 → 54 → 53 → …                   ← 逐字节滑动，说明在算摘要
```

`[HP]` 那组是**按字节滑动**的，说明有一段代码在对"安装路径 + `_IJM_2019…`"
这个字符串做摘要。如果资产密钥是从这类**运行时字符串**推出来的，
它就必然与"安装路径 / 包名后缀 / 签名"中的某一项绑定——而这三项在重打包样本上都不等于原厂值。

> **可证伪的预测**：
> 把样本装成与原厂**相同的包名与路径**（只在签名上做最少改动），重跑并比较捕获到的 16 字节密钥。
> - 若密钥变成另一个值、且 80 字节这次解出**合法填充** → 假设成立，密钥是运行时派生的；
> - 若密钥一字不变 → 假设被否，密钥是静态派生的；那么"填充不成立"就只剩
>   "这 80 字节不是 SM4 密文"这一种解释（回到 #14 的 ②）。
