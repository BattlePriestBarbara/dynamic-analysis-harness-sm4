# 02 静态拆解

这一章是"不执行一行代码"能得到的全部结论。所有数字均来自对样本目录的直接测量。

## 2.1 清单与签名

`AndroidManifest.xml` 是二进制 AXML（117,056 B，解码后 2,037 行）。

| 项 | 实测值 | 评价 |
|---|---|---|
| 编译 / 目标 SDK | compileSdk 33 / minSdk 21 / targetSdk 32 | 目标 SDK 偏低（32），未按新版本要求收紧 |
| `allowBackup` | `false` | ✓ |
| `debuggable` | 未声明（=false） | ✓ |
| `usesCleartextTraffic` | `true` | ✗ 允许明文 |
| `networkSecurityConfig` | 仅 `base-config cleartextTrafficPermitted="true"`，无 `domain-config` / `pin-set` | ✗ |
| `largeHeap` | `true` | 中性 |
| 权限 | 90 项（含 2 项**非法权限名**） | 见 [09](09-风险清单与攻击面.md) |
| 签名算法 | `SHA1withRSA` + **1024-bit RSA** | ✗ 弱 |
| 证书有效期 | 2010-12-19 → 2065-09-21 | 超长有效期，非 EV |
| 证书主体 | `CN=<redacted>, OU=<redacted>, O=<redacted>` | 与开发团队标识相关，已脱敏 |
| 证书 SHA-256 | `<REDACTED-CERT-SHA256>` | 可用于重打包检测，已脱敏 |

两个**非法权限名**：把 `MediaStore.Images.Media.INTERNAL_CONTENT_URI` 和
`Manifest.permission.MANAGE_DOCUMENTS`（后者是常量名而非权限名）当权限声明了。
系统会静默忽略，无实际风险，但反映出清单是**由代码常量直接拼出来的**。

### AXML 解析的一个技巧

`aapt` 只接受 zip 容器，而样本是目录。做法：把 `AndroidManifest.xml` + `resources.arsc`
塞进一个**最小 APK**，再用 `aapt dump badging / xmltree`：

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
[IO.Compression.ZipFile]::CreateFromDirectory($tmp, "probe.apk")
aapt dump badging probe.apk
aapt dump xmltree probe.apk AndroidManifest.xml
```

副产品：`aapt2` 的告警会同时打印**旧资源路径**与资源 ID——这为后续"资源名还原"留了口子（见 §2.8 末）。

## 2.2 主 DEX：4 个类讲完整个壳

`classes.dex` 只有 **13,912 B / 4 个类**：`s.h.e.l.l.{A,C,N,S}`。

| 类 | 关键方法 | 作用 |
|---|---|---|
| `S` | `attachBaseContext`、`ls`、`al` | 装载入口；`al` 是 **native** |
| `A` | `getAssets`、`getResources` | 资源代理 |
| `N` | `l`、`r`、`ra`、`b2b` | 载荷解密 / 注入（均 native） |
| `C` | `i(I)V`（native） | 状态计数，无业务语义 |

三处值得记下的细节：

1. **双路径兼容**：`attachBaseContext` 里反射拿 `LoadedApk.getApplicationInfo()`；
   `ls(ApplicationInfo)` 用 `dataDir + "/files"` 建目录并把 `sourceDir` 写进静态字段。
   Android 9+ 走 `AppComponentFactory`、8- 走 `ClassLoader`，两条路都留了。
2. **垃圾指令插入**：四个类里大量出现
   `new-instance Object; invoke-direct Object.<init>; if-eqz; invoke-virtual Object.hashCode`
   这种无语义序列（`<clinit>` 6 次、`a()` 4 次），目的是破坏控制流图与反编译变量推断。
   **不影响语义**——这是读壳代码时最容易被带偏的地方。
3. **真实入口不在明文里**：`com.<vendor>.mobilebank.per.app.MBApplication` 这个类
   在明文 DEX 中根本不存在，它由 native 层解密后注册。

> 结论：**主 DEX 的存在意义只是"让 ART 能加载一个 Application 并调用 native"**。
> 想在 DEX 层找业务逻辑是方向性错误。

## 2.3 三个加密容器（实测结构）

| 文件 | 大小 | 整文件熵 | 64 KiB 块熵 | 头部特征 |
|---|---:|---:|---|---|
| `ijiami.dat` | 13,525,562 | **7.987** | 7.70 – 8.00 | `04 00 00 00` + `04 46 2f 03` + 32 位十六进制串 + 长度字段 |
| `ijiami.ajm` | 6,917,852 | **7.995** | 7.99 – 7.99 | 魔数 `indl01`，随后 `0x00032b68`(207,720) / `0x00698ec4`(6,918,852) / `0x00ddfc54` |
| `IJMDal.Data` | 1,372,784 | **8.000** | 8.00 – 8.00 | 纯随机，无明文头 |

三点判读：

- `ijiami.ajm` 里的 `0x00698ec4` 与文件长度只差 1,000 字节，像是"含头总长"；
  `0x00032b68` 像"头长"或"明文长度"。**未动态验证前不下结论。**
- 魔数扫描（`dex\n03x`、`PK\x03\x04`、`\x1f\x8b`、`\x7fELF`、`cdex`）在三者中**零命中真实结构**；
  命中的 `78 9C/78 01/78 DA` 数量与随机数据的期望同量级 → **判定为误报，不是 zlib 流**。
- `IJMDal.Data` 后来被专门做过熵分析（[06 §6.2](06-VMP与CFF取证.md)）：
  全局 H = 7.99986，滑窗中位数 7.591 对随机零假设 7.5904±0.0341（z = −0.52），
  1.37 MB 内**没有任何熵边界**、没有 ≥64 B 的零串或可打印串。
  → 它在任何偏移上都没有藏明文容器。

> 也就是说：三个容器都是**整文件加密**，静态抠不出 DEX，也抠不出中间载荷。

## 2.4 `libexec.so` 的三层反静态设计

对加固运行时（791,584 B）做 ELF 级检查，得到三个互相印证的异常。这是全篇最关键的静态发现。

### (1) 节头伪造：`.dynsym` 只报 3 项，真实 539 项

| 来源 | 符号数 |
|---|---:|
| 节头 `.dynsym`（`sh_size = 72`） | **3**（1 空 + `__cxa_atexit` + `__cxa_finalize`） |
| `DT_HASH`（`nbucket = 539, nchain = 539`，文件偏移 `0x4578`） | **539** |
| 实际可读出 | 375 个定义符号 + 164 个导入 |

Android 链接器用 `DT_HASH` / `DT_GNU_HASH`，**不看节头**，所以设备上一切正常；
而 IDA / Ghidra / `readelf` 默认信节头，于是只看到 2 个导入，误判"无导出、无 JNI"。

Ghidra 首次导入时刷屏的正是这条：

```
ELF Relocation Error: Type = 257 (0x101) at 001f8258 (Symbol = <no name>) - Invalid symbol index (503)
```

—— 重定位引用了第 503 号符号，而节头只声明了 3 个。**这条报错本身就是证据**。

### (2) 从 `DT_HASH` 恢复的真实导出

| 符号 | 地址 | 大小 | 意义 |
|---|---|---:|---|
| `ijiami` | `0x72d80` | 4 | 厂商标记（内容是随机字节，不是字符串） |
| **`JNI_OnLoad`** | **`0x72e74`** | **120** | JNI 入口 |
| `ijm_vmp` | `0x11b588` | 4 | VMP 标记（一个 OBJECT，位于第二个 `PT_LOAD`） |
| `__aarch64_sync_cache_range` | `0xe12c0` | 124 | 缓存同步（自解密必备） |
| `__emutls_get_address` / `__emutls_register_common` | `0xe14b4` / `0xe160c` | 344 / 60 | TLS 模拟 |
| `__dynamic_cast` | `0xdb930` | 320 | C++ RTTI |

### (3) 代码段是密文，只有 `DT_INIT` 是明文

- 段布局：`LOAD(RX)` 覆盖 `0x0–0x98C84`；`LOAD(RW)` 覆盖 `0xF35D0–0x1191A4`；
  **中间 `0x98C84–0xF35D0` 是空洞**。
- 但符号表把 `__aarch64_sync_cache_range`(`0xe12c0`)、`__dynamic_cast`(`0xdb930`)
  指向**空洞**——符号地址与段布局自相矛盾，这又是一层误导。
- 字节统计（791 KB）：

| 特征 | 命中 | 正常 C++ 库预期 |
|---|---:|---|
| `ret`（`c0 03 5f d6`） | **7** | 数千 |
| `stp x29,x30,[sp,#-0x10]!`（`fd 7b bf a9`） | **0** | 数百 |
| `bl`（`?? ?? ?? 94`） | 98 | 数千 |
| 全文件熵 / 代码段熵 | 6.47 / 6.82 | 5.5 – 6.2 |

- 在 `JNI_OnLoad`(`0x72e74`) 处按 ARM64 解码得到 `cpyert`、`ld1sw {z20.D}` 等 **SVE 指令**——
  在 Android 上没有意义，说明该处字节**不是合法 ARM64 代码**。
- 唯一"像代码"的位置是 `DT_INIT = 0x985A0`：

```
0x1985A0  stp  x0,x1,[sp,#-0xc0]!
0x1985A4  stp  x2,x0,[sp,#0x10]
0x1985A8  str  x30,[sp,#0x28]
0x1985AC  bl   0x1987B4
...
0x1985E4  dc   CVAU, x0        ← 清理数据缓存
0x1985E8  ic   IVAU, x0        ← 使指令缓存失效
0x1985EC  add  x0,x0,#0x40
0x1985F0  cmp  x0,x1
0x1985F4  b.cc 0x1985E4        ← 循环刷 cache
0x198600  ret
```

`DC CVAU` + `IC IVAU` 循环是"把解密后的字节写回代码段并刷新指令缓存"的标准手法。
（地址前缀 `0x1…` 是 Ghidra 的镜像基址产物，实际值见 [99 附录](99-附录-术语与地址速查.md)。）

**综合判定（已证）**：该库采用"**部分加密 + 启动期自解密 + VMP 标记 + 节头/符号表伪造**"的组合保护。
磁盘上的业务代码不可静态反汇编；`JNI_OnLoad` / `N.l` / `N.b2b` 的真实语义**必须运行时观察**。

同类（带 `ijiami` 标记且导出为空）的还有 `libPassGuard.so`（密码键盘）、`libGMEncrypt.so`（国密）、
`libentryexpro.so`——**密码键盘与国密实现也在同一保护下**。

## 2.6 支付安全沙箱：PA / MicroDroid

`assets/library-release-signed_*.pa` 是一个 ZIP（3,081,744 B，9 个条目）：

| 条目 | 大小 | 内容 |
|---|---:|---|
| `Manifest.xml` | 979 | 自定义清单（非 AXML）：`<application version="2">`（注释：1 = AVF PA，**2 = 轻量沙箱 PA**） |
| `permission.json` | 502 | **能力声明 + 证书绑定** |
| `provider.properties` | 81 | `implementation-class=com.example.demo.MyProvider`（**模板残留**） |
| `cipher` | 619 | 加密参数（疑似密钥材料） |
| `IssuerCA` | 1,606 | 签发 CA |
| `dictionary` | 47 | 资源字典 |
| `properties` | 184 | `dictionary=<sha256>`、`oppo0.dex=<sha256>`（哈希清单） |
| `oppo0.dex` | 10,160 | 已加密 |
| `classes.dex` | 3,109,480 | **已加密**（无 `dex\n` 魔数，头部即随机） |

`permission.json` 关键结构：

```json
{
  "paId": "com.<vendor>.sandbox.secure.pa",
  "abilities": [
    { "name": "com.<vendor>.sandbox.secure.ISecureDataCallback",
      "flags": "android|microdroid",
      "certs": ["5B87EC1D…"] },
    { "name": "com.<vendor>.sandbox.secure.ISecureInterface",
      "flags": "android|microdroid",
      "certs": ["5B87EC1D…"] }
  ]
}
```

三点解读：

- `flags` 同时允许 `android` 与 **`microdroid`** → 在支持 pKVM 的机型上跑 **AVF / MicroDroid 虚拟机**，
  支付敏感逻辑与主系统隔离；不支持时退化为同机沙箱。
- 两个 AIDL 接口**只接受证书 SHA-256 = `5B87EC1D…` 的调用方**，属于进程间调用的证书级鉴权。
- 沙箱载荷（`classes.dex`）加密存放，由 PA 运行时解密。

> 这是本次分析中**架构层级最高**的发现：该客户端的支付安全不止"加固 + 风控"，
> 还引入了**硬件虚拟化隔离**与**证书级 IPC 鉴权**。

### 一个可复用的资源名还原思路

### 传输安全（实测）

`AndroidManifest.xml` → `android:networkSecurityConfig=@0x7f140016` → `xml/<vendor>_network_security_config`，
其 AXML 解码结果（264 字节全文）：

```
字符串池: "base-config", "cleartextTrafficPermitted", "network-security-config"
→ <network-security-config>
      <base-config cleartextTrafficPermitted="true"/>
```

- **没有任何 `domain-config` / `trust-anchors` / `pin-set` / `debug-overrides`**；
- 清单另有 `usesCleartextTraffic = true`；
- 结论：**全 App 允许明文 HTTP，且未见声明式证书绑定**。
  是否存在**代码级** pinning（OkHttp `CertificatePinner`）无法从加密主 DEX 确认 → **记为"未验证"**。
