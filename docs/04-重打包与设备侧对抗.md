# 04 重打包与设备侧对抗

## 4.1 为什么先走"设备"而不是仿真

静态已证明代码是密文，必须让壳自己解密。最自然的想法是"在真机/模拟器上跑起来，然后 dump 内存"。
于是先搭了设备侧环境。结论提前说：**这条路被"完整性校验 + 裸 syscall 退出"封死**，
但它产出了两条极有价值的负面结论（见 §4.5、§4.6），也为后续仿真路线提供了对照。

## 4.2 重打包流水线（已验证可安装）

样本是解包目录，必须先重新打成 APK 才能安装：

1. **重打包**：Python `zipfile`；`.so` 与 `resources.arsc` 用 **STORED**（配合 `zipalign -p 4`），其余 deflate
   → 5,158 项 / 221.2 MB / 12 秒。
2. **对齐**：`zipalign -p -f 4` → 221.8 MB。
3. **签名**：`apksigner.jar`（build-tools 34.0.0，自签，`CN` 由脚本任意生成）→ v1 + v2 + v3。
4. **安装**：`adb install -r -g` → `Success`。

**回读校验**（`aapt dump badging`）：包名、versionCode、minSdk/targetSdk、`native-code`、入口 Activity
全部与原始一致 → 资源表与清单在重打包后依然完整。

> 这一步的意义：证明"我们改的不是包结构，而只是签名与压缩方式"。后续一切异常都可归因于壳，而不是打包错误。

## 4.3 模拟器环境

| 项 | 实测值 |
|---|---|
| 模拟器 | 支持 `adbDebug` 与 `rootMode` 的 Android 9 实例 |
| 系统 | Android 9 / SDK 28 |
| ABI 列表 | `x86_64,x86,arm64-v8a,armeabi-v7a,armeabi`（**带 arm64 原生翻译层**，可跑 arm64-only 包） |
| root | `/system/bin/su` 可用，`getenforce = Permissive` |

**一个踩过的坑**：Frida MCP 的 `usb` 选择器在"USB + TCP 双 transport"环境下会选错，

## 4.4 壳的运行行为（本次核心观测）

时间线（多次重复一致）：

```
t = 0      进程启动
t = 90–250 ms  libnb 完成 arm64 翻译
               → 壳把 libexec.so / libexecmain.so 释放到 files/ 并加载
               → 进程静默死亡
```

日志特征：

```
ActivityManager: Process <pkg> (pid N) has died
Zygote: Process N exited due to signal (9)
```

**没有** tombstone、**没有** `Fatal signal`、**没有** Java 异常栈。
信号链（Frida 实测）：

```
raise(19=SIGSTOP)            ← 调用者 boot-framework.oat+0x3c40ee
  → tgkill(pid, pid, 19)     ← 自伤
```

把 `tgkill/kill` 替换为"只吞 9/19/6"之后**仍然死亡** → 真正的退出走
**裸 `SVC` 指令或 `exit_group`**，绕过 libc 导出表，用户态 hook 拦不到。

死前的文件行为：

- `base.apk` 被连续 `open` **4 次**（典型 META-INF 验签读取）；
- 证据目录只落 `cache/proc_auxv`（304 B，反调试 auxv 快照）；
- **无任何落盘 dex** → 主 DEX 纯内存加载（`InMemoryDex` / `openDexFile`）。

**关键对照实验**：不用 Frida、直接 `am start` 启动，同样自杀
→ **这不是 Frida 检测，而是完整性 / 环境校验**。

## 4.5 四条对抗路线与结果

| 手段 | 做法 | 结果 |
|---|---|---|
| **Java 层签名伪造** | 从 `META-INF` 的 PKCS#7 解出原始证书，注入 `getPackageInfo` / `getInstalledPackages` 的 `GET_SIGNATURES` | 返回的 `len` / 主体 / `sha1` 与原始**完全一致**，但**钩子从未被调用** → 校验不走 Java API |
| **APK 路径重定向** | 把 `/data/app/…/base.apk` 的 `open`/`openat`/`fopen` 改写到同内容伪造文件（221 MB + 原始 META-INF） | 命中 2 次，壳仍自杀 |
| **保留原始 META-INF + 仅 v2 签名** | `apksigner --v1-signing-enabled false` | 该工具**仍会删除** `META-INF/MANIFEST.MF / *.SF / *.RSA`（实测签名后该目录为空）→ 此路不通 |
| **Frida 17 无 Java bridge** | 用 `frida-java-bridge` + `frida-compile` 自编译 agent（748 KB） | 解决：`java: true`、`SDK_INT=28`，Java 层钩子可用 |

### 为什么"路径重定向"注定失败（重要）

壳比对的是 **v1 签名里的逐条目摘要**。而本样本的 `res/` 已被**混淆改名**：

```
MANIFEST.MF 记的是   res/-NH.xml
磁盘上实际是         res/1E_.png
```

→ 条目名与内容哈希**无法同时复刻**，任何重打包版本都无法通过 v1 逐条目校验。
**这不是"手段不够强"，而是样本的形态让这条路在信息层面不可行。**

### 为什么"Java 层签名伪造"注定失败

钩子一次都没被调用，说明校验发生在**native 且不经过 Java API**。
这也解释了为什么后来 unidbg 路线能成功：仿真器直接把 native 环境"喂"给壳，绕过了整条校验链。

## 4.6 这一阶段的负面结论（价值最高的部分）

1. **x86_64 + arm64 翻译层上，壳的反调试与完整性校验先于解密执行**，并以裸 syscall 退出
   → 用户态 hook 无效，`SIGSTOP` 处理是死路。
2. **"换真机"也不是银弹**：完整性校验依赖 v1 逐条目摘要，样本已被改名，真机同样过不去
   （除非拿到**原始未解包 APK**）。
3. 结论因此变成：**不要试图满足校验，要绕过校验** → 这才有了 [05 unidbg](05-unidbg仿真与native脱壳.md)。

## 4.7 为 arm64 准备的 Frida agent（未执行）

即便当轮未用上，agent 仍然写完了并做了**无设备单元测试**（16 条断言全过），要点：

- 不硬编码 `al` 的地址：hook `RegisterNatives` → 读 `JNINativeMethod` 数组 → 取真实 `fnPtr`；
- 晚 attach 时用 `fnPtr − 0x77134` 反推模块基址，并用 `\x7fELF` 校验；
- 支持两种 dump 路径：`RegisterNatives` 精确命中，或 `--sweep` 扫全部 `ClassLoader`；
- 明确的已知限制：`ptrace` 可被中和，但 `/proc/self/maps` 扫描仍会看到 agent；
  `scanMemory` 同步执行有 ANR 风险（默认 768 MB 预算，跳过 `/system` `/apex` `/vendor` `/product`）；
  只匹配 `dex\n03x`，不匹配 `cdex`。

> 这段工作的意义：**把"下一步要做什么"变成可执行代码**，即使当轮没用上。
> 后来真要走真机路线时，成本从"从零写"降到"跑一遍"。
