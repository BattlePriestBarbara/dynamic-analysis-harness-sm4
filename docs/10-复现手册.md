# 10 复现手册

所有命令用占位符（含义见 [SANITIZATION §2](../SANITIZATION.md)）。
**顺序很重要**：后一步依赖前一步的产物。

## 10.1 前置条件

| 项 | 要求 |
|---|---|
| 样本 | 解包后的客户端目录，位于 `<SAMPLE>` |
| build-tools | 34.0.0（`aapt`、`aapt2`、`dexdump`、`zipalign`、`apksigner`） |
| Python | 3.12（本项目用 `py -3.12` 显式调用） |
| Ghidra | 12.1.3（headless 可用） |
| unidbg | 0.9.10-SNAPSHOT（已编译，依赖齐全） |
| Frida | 17.18.0（仅设备路线需要） |
| 设备 | 可选；Android 9 / SDK 28 以上、可 root |

## 10.2 静态拆解

```powershell
# 1) 让 aapt 接受一个目录：先造一个最小 APK
Add-Type -AssemblyName System.IO.Compression.FileSystem
[IO.Compression.ZipFile]::CreateFromDirectory($tmp, "probe.apk")   # tmp 内放 AndroidManifest.xml + resources.arsc
aapt dump badging probe.apk
aapt dump xmltree probe.apk AndroidManifest.xml > manifest_tree.txt

# 2) 清单结构化
py -3.12 <OUT>/parse_manifest.py

# 3) DEX
dexdump -f -h -d <SAMPLE>/classes.dex > classes_dexdump.txt
dexdump -d <SAMPLE>/assets/RiskStub.dex > riskstub_dexdump.txt
py -3.12 <OUT>/dex_parse.py <SAMPLE>/assets/RiskStub.dex riskstub.json

# 4) 原生库盘点（136 个 so，约 2 秒）
py -3.12 <OUT>/elf_scan.py

# 5) 载荷熵 + 魔数
py -3.12 <OUT>/payload_probe.py

# 6) 域名收割（206 MB 文本，30 秒量级）
py -3.12 <OUT>/harvest_urls.py

# 7) 签名
keytool -printcert -file <SAMPLE>/META-INF/ANDROID_.RSA
```

## 10.3 从 `DT_HASH` 恢复真实符号

```powershell
# 读 DT_HASH（偏移 0x4578，nbucket=nchain=539）→ 得 JNI_OnLoad = 0x72e74
analyzeHeadless.bat <GHIDRA_PROJ> <project> `
  -import <SAMPLE>/assets/ijm_lib/arm64-v8a/libexec.so `
  -postScript FixExec.java `
  -scriptPath <OUT>/ghidra_scripts
```

**预期**：导入时会刷屏 `Invalid symbol index (503)`。
这不是失败——**它本身就是"节头伪造"的证据**（见 [03](03-Ghidra与反静态对抗.md)）。

## 10.4 重打包与设备（可选）

```powershell
py -3.12 <WORK>/repack.py                       # 5,158 项 / 221.2 MB
zipalign -p -f 4 in.apk out.apk                 # 221.8 MB
java -jar apksigner.jar sign --ks <ks> --out signed.apk out.apk
adb install -r -g signed.apk
aapt dump badging signed.apk                    # 回读校验
```

**预期**：安装成功，启动后 90–250 ms 静默死亡（`signal 9`，无 tombstone）。
这是壳的完整性校验，不是安装失败（见 [04](04-重打包与设备侧对抗.md)）。

## 10.5 unidbg 仿真（核心步骤）

```powershell
# 1) 编译
cd <UNIDBG>
mvn -q -DskipTests package

# 2) 跑初始化 + 抓取（务必重定向 stdin，否则调试器会阻塞）
java -cp "<cp>" <harness>.Emulator < empty_stdin.txt > run_stdout.txt 2> run_stderr.txt

# 3) 只要 SM4 自测（隔离验证，最快）
java -D<prefix>.sm4selftestOnly=true -cp "<cp>" <harness>.Emulator < empty_stdin.txt

# 4) 抓取前保留旧文件（默认关）
java -D<prefix>.sm4dyn.keep=true -cp "<cp>" <harness>.Emulator < empty_stdin.txt

# 5) 纯观测（关闭索引旁路）
java -D<prefix>.wlBypass=off -cp "<cp>" <harness>.Emulator < empty_stdin.txt
```

**预期产物**：

| 文件 | 大小 | 校验点 |
|---|---:|---|
| `libexec_image.bin` | 1,163,264 | sha256 前缀 `d2153f570eb7e38c` |
| `register_natives.tsv` | 914 | 11 行 + 表头 |
| `sm4_key_dynamic.bin` | 16 | 只有走到 `setkey` 才有内容 |
| `wrapper_callsite.jsonl` | — | 含路径字符串与暂存缓冲 |

**两个已知坑**（都伪装成"卡死"）：
1. 不重定向 stdin → `SimpleARM64Debugger` 调 `Scanner.nextLine()` 永久阻塞；
2. 上一次成功运行后，若本次没走到 `setkey`，抓取文件会被**覆盖成空**（用 `keep` 规避）。

## 10.8 仿真器开关一览

| 开关 | 默认 | 用途 |
|---|---|---|
| `<prefix>.sm4selftestOnly` | false | 只跑 SM4 自测后退出 |
| `<prefix>.sm4dyn.keep` | **false** | 抓取前把旧文件改名 `.bak` 而非截断 |
| `<prefix>.sm4key` | 空 | 手动指定 16 B 密钥（十六进制） |
| `<prefix>.wlBypass` | on（两个名字） | `off` = 纯观测；`all` = 对所有名字强制走索引探针 |
| `<prefix>.wlName` | 空 | 把 wrapper 的两个名字缓冲改写成指定资产 |
| `<prefix>.fixHashInit` | **true** | 索引构建前清零哈希表（恢复 `calloc` 语义）。**关掉会重现 4,424 条的假缺口** |
| `<prefix>.fixHashSpin` | true | 探测空转兜底（触发时清零整表）。修好 `fixHashInit` 后不应再触发 |

## 10.9 复现边界（必须读）

1. **仿真结果 ≠ 真机行为**。仿真器跳过了完整性校验，因此所有运行时结论只在
   "过了校验之后"的语境下成立。
2. **重打包会破坏 v1 逐条目摘要**，因此设备侧永远过不了校验（除非用原始未解包 APK）。
3. ~~索引缺口尚未修复，因此目标 blob 至今未能被解出~~ → **已修复**：缺口是本仓库 harness
   的清零 hook 造成的（[08 §8.13](08-APK内部索引缺口.md)）。复现时注意
   `<prefix>.fixHashInit`（默认开）——它把清零从"构建中途"搬到"构建第一个插入之前"；
   关掉它会重现 4,424 条的假缺口。
4. 即使索引完整，目标 80 字节仍不是一把密钥 + 一种模式能解开的明文（[07 §7.12](07-SM4链路逐跳定位.md)），
   所以"能取到"与"能解出"是两件事，不要混为一谈。
4. 版本号已模糊化（`v15.x`），复现需自行确认样本版本（用 5,161 条目 / 289,847,817 B /
   单 ABI 这三个结构指纹比对）。
