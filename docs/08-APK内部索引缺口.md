# 08 APK 内部索引缺口（当前唯一硬阻塞）

## 8.1 现象

壳的资产闸门（`0x12073180`）对目标名字返回"不存在"，于是整条解密链被跳过。
但闸门查的不是文件系统——**APK 里明明有这个条目**。

## 8.2 先证明断点在"索引"，不在下游

一条决定性的日志：**过了闸门之后仍然 0**。

```
gate(<name>) → 0（放行）
reader(...)  → ptr=0, len=0      ← 取不到
```

配合 [07 §7.10](07-SM4链路逐跳定位.md) 的旁路对照（强制指定一个**索引内**的名字 → 全链路跑通），
可以把"密码学、reader、输出"全部排除，**阻塞点唯一落在索引**。

## 8.3 索引到底覆盖了多少：两条独立走查

用两种**互不依赖**的方法核对 ZIP 结构，避免单一失败模式解释结果。

### A 覆盖法（相信中央目录）

对每个中央目录条目，按它声明的偏移读 4 字节：

> **5,161 / 5,161 全部是 `50 4b 03 04`，漂移 0。**

→ 中央目录**没有说谎**，这个 ZIP 是自洽的。

### B 走查法（不信中央目录）

在全部 **232,579,361** 字节里裸扫 `PK\x03\x04`，解析每个局部头并取其文件名：

> **5,162 个命中，5,161 个不同名字，无重复。**

A 与 B 的差值只有 1 个——而那个 1 正是下面这个陷阱。

## 8.4 一个假阳性，和它教给我们的方法

B 多出来的头在偏移 **`0x3001f46`**，名字 `CacheList.json`。它看起来像一个"隐藏条目"，**但不是**。

真实情况：

```
条目      assets/CacheList/CacheList.json.zip
压缩方式  deflate, csize = 61,370
局部头    0x3001f00
数据起点  0x3001f41
裸 inflate 该区间 → 61,465 B，开头就是 "PK\x03\x04 … CacheList"
```

那个"局部头"是**压缩流内部的 ZIP 字面量**。

> **方法论（已写入 [12](12-经验与教训.md)）**：
> 在 deflate 数据上裸扫魔数会"发明"文件；**边界检查不是可选项**。

## 8.5 缺口的精确形状

把索引里的 4,424 个名字与中央目录的 5,161 个做集合运算：

```
omitted == { header_offset < 0x511c9c4 }       精确成立，737 / 737
last omitted    0x50a78ff   assets/qbar/detect_model.bin
first kept      0x511c9c4   assets/qbar/detect_model.param
delta 直方图    [(0, 737)]        ← 每个被略过的条目都对得上，无一处偏移
```

**这是全章最重要的一个等式**：缺口不是"某些资源"，而是**一个偏移窗口**：

```
索引 = [0x511c9c4, EOF)
```

配平关系：

```
5,161 (总数)  −  4,424 (索引)  =  737 (缺口)
0x1429        −  0x1148        =  0x2e1
```

## 8.6 因此三个解释当场死亡

| 原假设 | 为什么死 |
|---|---|
| 重打包把偏移挪了 | 漂移 **0**，不是"偏移变大" |
| 索引是"名字/类型白名单" | **过滤器不可能落成连续的偏移前缀**；且缺口里包含 `AndroidManifest.xml`、`resources.arsc` 和全部 71 个 `META-INF` 条目 |
| 那 737 个条目的数据本身不存在 | 5,161 个真实局部头俱在；**有中央目录条目但无数据的数量 = 0** |

## 8.7 两个仍然存活的机制（尚未分离）

| 代号 | 机制 | 含义 |
|---|---|---|
| **M1** | 走查游标**从 `0x511c9c4` 开始** | 索引是一次"从某个点往后扫"的产物，前面的部分没进 |
| **M2** | 索引**只覆盖打包器追加的段** | 低半区是"原始内容"，高半区是"打包器加上去的"，索引只描述后者 |

**一个反对 M2 的数字**：目标 blob（`assets/sign_verify.png`）位于 `0x28ef192`，
**远低于**边界 → 它属于那 737 个。而它恰恰是 wrapper 唯一硬编码的目标。
如果低半区是"未被触碰的原始内容"，wrapper 在那里就没有东西可解。

> 所以 M1 更像是真的，但**还不能定论**——需要的不是更多推理，而是**读出索引头的
> `start` / `count` 字段语义**。这就是下面这条新证据的意义。

## 8.8 新证据：索引头里有一个"数字打架"

> **⚠ 本节"数字打架"的结论已被 §8.12 更正（缺口本身仍成立）。**
> 保留原文是为了让"错在哪一步"可追溯——这正是本仓库的写法。

在仿真输出里找到了索引头的 dump：

| 项 | 值 |
|---|---|
| dump 位置 | 运行日志 `run5_stdout.txt` 第 275 行 |
| 内存地址 | `0x12819080`，**12 × 8 字节 = 0x60** |
| 对应索引基址 | `0x12119710` |
| 头长度 | `0x40`（前 8 个 qword 是头，后面是槽位起点） |

**关键判别发现**：

```
头内 +0x30 处的字  =  0x1429  =  5,161   ← 等于中央目录全量
索引实际活跃槽位   =          4,424   =  0x1148
```

→ **头部声称"我有 5,161 条"，索引实际只有 4,424 条**。这是一个**内部不一致**，
而不是"打包器只处理了高半区"的自然结果：

- 若是 M2（只描述追加段），头里那个计数**应该**是 4,424；
- 它写的是 5,161，说明**写入方本来打算写 5,161 条**，实际写少了 737 条。

这把天平明显推向 **M1（游标起点问题）**，但仍需读到 `start` 字段才能确认
（`+0x30` 是 `count` 还是别的语义，取决于对加载函数 `FUN_00182f48` 的完整解读）。

> 状态：**已定位、未定性**。这是本仓库当前的第一优先 work item。

## 8.9 三条路线的取舍

| 路线 | 做法 | 状态 |
|---|---|---|
| **A** | 给索引**补一条记录**（目标 blob） | **唯一剩下的路**，且成本低 |
| B | 重建索引（按当前文件重新生成） | **不必要**：已证明 4,424 条在本文件上完全有效（漂移 0） |
| C | 找回原始 APK 以取得"正确"偏移 | **不必要**，且样本形态（已解包、名字被改名）让此路不可行 |

### 路线 A 为什么便宜

索引槽位的布局已经被验证过：每个记录相对槽位指针的 **`-0x24 .. -0x4`** 是**六字段**结构，
且在本文件上**逐条自洽**（4,424 条全部通过一致性检查）。所以补记录不需要"发明格式"，
只需**复制一个相邻槽位并改写六个字段**。

需要写入的字段（语义已由相邻记录反推，待补测确认）：

1. 名字（或名字在字符串区的偏移）
2. 名字长度
3. 局部头偏移
4. 压缩后长度
5. 解压后长度
6. 标志位（压缩方式 / 是否为目录）

> **注意一个诚实的前提**：这六字段的**语义**是从相邻记录一致性反推的，
> 不是从代码读出来的。补记录成功后必须**回读验证**（闸门返 0 且 reader 拿到字节），
> 否则只是"写进去了"而不是"写对了"。

## 8.10 这一步**没有**回答什么

1. ~~`+0x30` 是 `count` 还是 `capacity`~~ → **已答（§8.12）**：
   `+0x30` = EOCD 条目数 5,161，`+0x34` = 哈希容量 8,192。
2. 缺口是**写入时被截断**（只写了 4,424 条）还是**起点判定把前 737 条排除**——
   形状已证（§8.12 复测），**起点来源未证**。
3. 目标 blob 到底是密文还是签名块（依赖补记录后能否解出合法结构）。

## 8.11 本章小史（为什么值得单列一章）

这一章的内容**全部是在纠正一个错误结论之后得到的**：

- 早期把它写成"737 个受保护/被标记的资源"，并据此判定"路线 A 不可行"（极性错误）；
- 后来用"缺口 == 偏移前缀"这个等式把"保护名单"解释**证伪**；
- 再用"5161 vs 4424 vs 头部 0x1429"三个数字把机制收窄到"游标/计数不一致"。

> **教训**：当你说"某类资源被保护"时，先问一句"这个集合能不能写成 `{x | 某个连续数值条件}`"。
> 如果能，那它大概不是策略，而是**实现细节**。

## 8.12 更正：索引头已逐字段解码，推翻 §8.8 的"数字打架"

读完三个函数，并拿真实 APK 的 EOCD 逐字段对照后，`run5_stdout.txt` 第 275 行那
**12 个 word 的语义已经完全确定**——它不是打包器自建索引的头，而是
**ZIP 中央目录状态结构**（`int[16]`，即 `FUN_00184178` 的 `param_3`）。

### 解码结果（每一项都与文件实测值相等）

| 偏移 | 语义 | 日志值 | 独立来源 |
|---|---|---|---|
| `+0x00` (int) | `fd` | `3` | 首次 `open` 的返回值 |
| `+0x08` (u64) | `cd_offset` | `0x0DD7C1A7` | EOCD 偏移字段 = `0x0DD7C1A7` ✔ |
| `+0x10` (ptr) | 中央目录指针 | `0x130611A7` | `mmap_base + (cd_offset % 4096)` = `0x13061000 + 0x1A7` ✔ |
| `+0x18` (u64) | `cd_size` | `0x51F64` = 335,716 | EOCD 长度字段 ✔ |
| `+0x20` (ptr) | `mmap` 基址 | `0x13061000` | 页对齐 ✔ |
| `+0x28` (u64) | `mmap` 长度 | `0x5210B` = 336,139 | `0x1A7 + cd_size` ✔ |
| `+0x30` (int) | **条目数** | `0x1429` = 5,161 | EOCD 的两个条目数字段都是 5,161 ✔ |
| `+0x34` (int) | 哈希容量 | `0x2000` = 8,192 | `round_pow2(5161 × 4/3 + 1)` ✔ |
| `+0x38` (ptr) | 哈希表 | `0x1281B000` | 表项 16 B × 8,192 |

### 三个函数的职责（静态可证）

| 地址 | 作用 | 关键证据 |
|---|---|---|
| `FUN_00182f48` | open + 定位 EOCD | 先判 `size > 0x15`，把搜索窗夹到 **`0x10015` = 65,557**（22 + 65,535，正是 ZIP 注释上限） |
| `FUN_00184178` | 找 `PK\x05\x06`、`mmap` 中央目录 | 魔数 `0x04034b50` / `0x06054b50`；`mmap(NULL, (cd%4096)+cd_size, PROT_READ, MAP_SHARED, fd, cd-cd%4096)` |
| `FUN_00183190` | 建**名字哈希索引** | 逐条校验 `PK\x01\x02`、GP bit0（加密）、文件名含 `NUL`、`local_offset >= cd_offset`；**任一不满足即整建失败** |

哈希是 `h = h*31 + byte` 的 djb2 变体，开放寻址线性探测，掩码 `& (capacity-1)`。

### 撤回一半，保留一半

**撤回**（仅限 §8.8 的"数字打架"）：

- `+0x30` 不是"打包器声称有 5,161 条"，而是**从 EOCD 读出的条目数**。
  所以"头说 5,161、表里 4,424"不是同一字段的自相矛盾，而是**两个不同对象的数字**。

**保留**（§8.5 的缺口本身）——已用独立复测确认：

```
自写 CD 解析（本机复算）      : 5,161 条，其中 local_offset >= 0x511c9c4 的 4,424 条
运行时名字表 whitelist_names  : 4,424 条
CD \ runtime                  : 737 条
runtime \ CD                  : 0 条
SET EQUALITY (missing == {offset < 0x511c9c4}) : True
last  < bound : 0x50a78ff  assets/qbar/detect_model.bin
first >= bound: 0x511c9c4  assets/qbar/detect_model.param   ← 该偏移处确实是 PK\x03\x04
```

→ **缺口是真的，形状也是真的**：表里恰好缺"局部头偏移 < `0x511c9c4`"的那 737 条。
`0x511c9c4` 本身不是特殊标记，它就是 `detect_model.param` 这条记录的局部头偏移。

### 由此得到的唯一自洽解释

`FUN_00183190` 是**全量插入**（5,161 条任一非法即 `return -1`），所以它**不可能是**
产出这张 4,424 条表的构建者。真正的构建者只能是另一条路径（候选
`0x120833e8` / `0x12083af4`），而它在插入前有一个**起点判定**：
只处理 `local_offset >= 0x511c9c4` 的条目。

这也解释了为什么缺的是"按偏移排序的尾部之前的一整段"，而不是零散的 14%。
