# 08 APK 内部索引缺口：一个被自己的仿真器制造、又被它证伪的"硬阻塞"

> **⚠ 本章结论已在 §8.13 整体翻转。**
> 那 737 条"缺口"**不是 APK 的性质，也不是壳的行为**，而是本仓库自己的 unidbg harness
> 在索引构建过程中把哈希表清零造成的：清零发生在"已插入 737 条、还没插完"的瞬间，
> 于是先前那 737 条被抹掉，剩下的 4,424 条恰好都是"局部头偏移 ≥ `0x511c9c4`"的条目。
> 修复不到 10 行代码后，索引恢复 5,161 条，目标资产被壳**直接读到**，SM4 链路第一次真正跑通。
>
> §8.1–§8.12 保留原文（仅加注解），因为这一章真正的价值不是结论，而是
> **"一个自洽、可复现、连数字都对得上的错误结论，是怎么被自己的下一组证据推翻的"**。
> 如果你只读一节，读 [§8.13](#813-真正的成因harness-在构建中途清零了哈希表)。


## 8.1 现象

壳的资产闸门（`0x12073180`）对目标名字返回"不存在"，于是整条解密链被跳过。
但闸门查的不是文件系统——**APK 里明明有这个条目**。

## 8.2 先证明断点在"索引"，不在下游

一条决定性的日志：**过了闸门之后仍然 0**。

```
gate(<name>) → 0（放行）
reader(...)  → ptr=0, len=0      ← 取不到
```

配合 [07 §7.10](07-SM4链路逐跳定位.md) 的旁路对照（强制指定一个**索引内**的名字 → 全链路跑通），
可以把"密码学、reader、输出"全部排除，**阻塞点唯一落在索引**。

## 8.3 索引到底覆盖了多少：两条独立走查

用两种**互不依赖**的方法核对 ZIP 结构，避免单一失败模式解释结果。

### A 覆盖法（相信中央目录）

对每个中央目录条目，按它声明的偏移读 4 字节：

> **5,161 / 5,161 全部是 `50 4b 03 04`，漂移 0。**

→ 中央目录**没有说谎**，这个 ZIP 是自洽的。

### B 走查法（不信中央目录）

在全部 **232,579,361** 字节里裸扫 `PK\x03\x04`，解析每个局部头并取其文件名：

> **5,162 个命中，5,161 个不同名字，无重复。**

A 与 B 的差值只有 1 个——而那个 1 正是下面这个陷阱。

## 8.4 一个假阳性，和它教给我们的方法

B 多出来的头在偏移 **`0x3001f46`**，名字 `CacheList.json`。它看起来像一个"隐藏条目"，**但不是**。

真实情况：

```
条目      assets/CacheList/CacheList.json.zip
压缩方式  deflate, csize = 61,370
局部头    0x3001f00
数据起点  0x3001f41
裸 inflate 该区间 → 61,465 B，开头就是 "PK\x03\x04 … CacheList"
```

那个"局部头"是**压缩流内部的 ZIP 字面量**。

> **方法论（已写入 [12](12-经验与教训.md)）**：
> 在 deflate 数据上裸扫魔数会"发明"文件；**边界检查不是可选项**。

## 8.5 缺口的精确形状

把索引里的 4,424 个名字与中央目录的 5,161 个做集合运算：

```
omitted == { header_offset < 0x511c9c4 }       精确成立，737 / 737
last omitted    0x50a78ff   assets/qbar/detect_model.bin
first kept      0x511c9c4   assets/qbar/detect_model.param
delta 直方图    [(0, 737)]        ← 每个被略过的条目都对得上，无一处偏移
```

**这是全章最重要的一个等式**：缺口不是"某些资源"，而是**一个偏移窗口**：

```
索引 = [0x511c9c4, EOF)
```

配平关系：

```
5,161 (总数)  −  4,424 (索引)  =  737 (缺口)
0x1429        −  0x1148        =  0x2e1
```

## 8.6 因此三个解释当场死亡

| 原假设 | 为什么死 |
|---|---|
| 重打包把偏移挪了 | 漂移 **0**，不是"偏移变大" |
| 索引是"名字/类型白名单" | **过滤器不可能落成连续的偏移前缀**；且缺口里包含 `AndroidManifest.xml`、`resources.arsc` 和全部 71 个 `META-INF` 条目 |
| 那 737 个条目的数据本身不存在 | 5,161 个真实局部头俱在；**有中央目录条目但无数据的数量 = 0** |

## 8.7 两个仍然存活的机制（尚未分离）

| 代号 | 机制 | 含义 |
|---|---|---|
| **M1** | 走查游标**从 `0x511c9c4` 开始** | 索引是一次"从某个点往后扫"的产物，前面的部分没进 |
| **M2** | 索引**只覆盖打包器追加的段** | 低半区是"原始内容"，高半区是"打包器加上去的"，索引只描述后者 |

**一个反对 M2 的数字**：目标 blob（`assets/sign_verify.png`）位于 `0x28ef192`，
**远低于**边界 → 它属于那 737 个。而它恰恰是 wrapper 唯一硬编码的目标。
如果低半区是"未被触碰的原始内容"，wrapper 在那里就没有东西可解。

> 所以 M1 更像是真的，但**还不能定论**——需要的不是更多推理，而是**读出索引头的
> `start` / `count` 字段语义**。这就是下面这条新证据的意义。

## 8.8 新证据：索引头里有一个"数字打架"

> **⚠ 本节"数字打架"的结论已被 §8.12 更正（缺口本身仍成立）。**
> 保留原文是为了让"错在哪一步"可追溯——这正是本仓库的写法。

在仿真输出里找到了索引头的 dump：

| 项 | 值 |
|---|---|
| dump 位置 | 运行日志 `run5_stdout.txt` 第 275 行 |
| 内存地址 | `0x12819080`，**12 × 8 字节 = 0x60** |
| 对应索引基址 | `0x12119710` |
| 头长度 | `0x40`（前 8 个 qword 是头，后面是槽位起点） |

**关键判别发现**：

```
头内 +0x30 处的字  =  0x1429  =  5,161   ← 等于中央目录全量
索引实际活跃槽位   =          4,424   =  0x1148
```

→ **头部声称"我有 5,161 条"，索引实际只有 4,424 条**。这是一个**内部不一致**，
而不是"打包器只处理了高半区"的自然结果：

- 若是 M2（只描述追加段），头里那个计数**应该**是 4,424；
- 它写的是 5,161，说明**写入方本来打算写 5,161 条**，实际写少了 737 条。

这把天平明显推向 **M1（游标起点问题）**，但仍需读到 `start` 字段才能确认
（`+0x30` 是 `count` 还是别的语义，取决于对加载函数 `FUN_00182f48` 的完整解读）。

> 状态：**已定位、未定性**。这是本仓库当前的第一优先 work item。

## 8.9 三条路线的取舍

| 路线 | 做法 | 状态 |
|---|---|---|
| **A** | 给索引**补一条记录**（目标 blob） | **唯一剩下的路**，且成本低 |
| B | 重建索引（按当前文件重新生成） | **不必要**：已证明 4,424 条在本文件上完全有效（漂移 0） |
| C | 找回原始 APK 以取得"正确"偏移 | **不必要**，且样本形态（已解包、名字被改名）让此路不可行 |

### 路线 A 为什么便宜

索引槽位的布局已经被验证过：每个记录相对槽位指针的 **`-0x24 .. -0x4`** 是**六字段**结构，
且在本文件上**逐条自洽**（4,424 条全部通过一致性检查）。所以补记录不需要"发明格式"，
只需**复制一个相邻槽位并改写六个字段**。

需要写入的字段（语义已由相邻记录反推，待补测确认）：

1. 名字（或名字在字符串区的偏移）
2. 名字长度
3. 局部头偏移
4. 压缩后长度
5. 解压后长度
6. 标志位（压缩方式 / 是否为目录）

> **注意一个诚实的前提**：这六字段的**语义**是从相邻记录一致性反推的，
> 不是从代码读出来的。补记录成功后必须**回读验证**（闸门返 0 且 reader 拿到字节），
> 否则只是"写进去了"而不是"写对了"。

## 8.13 真正的成因：harness 在构建中途清零了哈希表

### 8.13.1 三条必须同时成立的观察

1. **整份日志里只有一次清零**，且落在构建窗口内部：
   第 199 行 `map loader(...)`（`zip_open` 入口）→ 201 行 `openat() -> fd 3`
   → **207 行 `zeroing 8192 slots (131072 bytes) at 0x1281b000`** → 274 行第一次 `probe #1`。
   这中间没有任何其它 harness 写内存的动作。
2. **这次构建必须是成功的**：`FUN_00182f48` 的失败路径会 close fd、munmap、
   `free(table)`，并把 `+0x30` / `+0x34` / `+0x38` 写成 `-1`、`-1`、`0`；
   而 dump 里 `+0x30 = 0x1429`、`+0x34 = 0x2000`、`+0x38 = 0x1281b000` 全部有效
   ⇒ 走的是"`FUN_00184178` 成功 **且** `FUN_00183190` 返回 0"的成功返回。
3. **成功 ⇒ 插入循环整整跑了 5,161 次**：`FUN_00183190` 的循环上界是
   `iVar4 = *(int *)(ctx + 0x30)`，而循环体内任一校验失败就 `return 0xffffffff`
   （会触发上面的失败路径）。所以"表里只有 4,424 条"**不可能**是"只插了 4,424 条"，
   只能是"插了 5,161 条，其中 737 条被抹掉"。

三条合起来只剩一种可能：**清零发生在构建过程中**。

### 8.13.2 决定性证据：把表内容逐槽位重放

如果清零发生在"第 737 条插入完成、第 738 条还没插"的瞬间，那么最终的表，
必须逐槽位等于**从第 737 条开始、在一张空表上重新构建**的结果。
把两种模型都重放一遍（djb2 `h = h*31 + byte`，`& 0x1fff`，线性探测），
再和日志里已经打印出来的 24 个槽位逐一对：

| 重放模型 | 活跃槽位 | 与日志中 24 个已打印槽位吻合 |
|---|---|---|
| **A**：第 0 条建到底（假定没被清零） | 5,161 | **11 / 24** |
| **B**：第 737 条建到底（假定清零在第 737 条之后） | **4,424** | **24 / 24** |

模型 B 同时命中**活跃槽位数**和**24 个槽位里各放着谁**。
这不是"看起来像"：A 模型连槽位内容都对不上（它多出的前 737 条会把后面所有条目挤到别的槽）。

于是 §8.5 那个"漂亮的等式"有了真正的解释：

```text
中央目录按 local_offset 升序排列
          +
被抹掉的是"最先插入的 737 条"（也就是偏移最小的 737 条）
          ⇓
剩下的 4,424 条 ≡ { local_offset >= 0x511c9c4 }
```

**`0x511c9c4` 不是任何东西的起点**，它只是第 737 条记录
（`assets/qbar/detect_model.param`）的局部头偏移。缺口"长得像一个偏移窗口"，
是"前缀被抹掉 + 目录按偏移排序"这两件事叠加出来的**幻觉**——
这正是它当初骗过了三个独立解释的原因。

### 8.13.3 为什么会清零：一个"兜底"被当成了正常路径

`+0x832b0` 是线性探测的循环头（`x20` = 表基址，`x28` = 容量−1 = `0x1fff`）：

```text
0x832a0  add x10,x20,w11,SXTW #4      ; &slot[h]       ← 每条记录都会执行一次
0x832a4  ldr x12,[x10]
0x832a8  cbz x12,0x832d0              ; 空槽 → 直接插入
0x832b0  sxtw x10,w12                 ; ← 探测步（harness 的计数器挂在这里）
0x832b4  add  x10,x10,#1
0x832b8  and  x11,x10,x28             ; (i+1) & mask
0x832bc  add  x10,x20,x11,LSL #4
0x832c0  ldr  x13,[x10]
0x832c8  cbnz x13,0x832b0             ; 非空 → 继续探测
```

harness 在 `+0x832b0` 上挂了个计数器：**累计 200,000 次就把整张表清零**，计数归零后继续跑。
这本来是防"脏表导致探测环死循环"的兜底（没有它，`JNI_OnLoad` 根本不会返回）。

问题在于：**这个兜底的触发门槛，正常构建永远达不到。**

```text
用同一份中央目录精确统计
  5,161 次插入 → 一共只执行 4,825 次探测步
  兜底阈值      → 200,000 次 = 4,825 的 41 倍
```

⇒ 能触发阈值的只有一种情形：表里有大量**非零脏槽**，探测在环上空转。
脏槽从哪来？`FUN_00183190` 用 `calloc(cap, 16)`（两个参数，count/size），
代码假定"槽位为 0 即空"；而 unidbg 交回来的这块内存并不为零——
harness 自己的注释记录了当时残留的内容：**`PK\x01\x02`（中央目录记录的字样）**。

也就是说，兜底不是被"更慢的正常路径"触发，而是被
**仿真器没有兑现 `calloc` 语义**触发；而它一触发，就顺便毁掉了已插入的 737 条。

### 8.13.4 修复：把清零从"构建中途"搬到"构建开始前"

只需要两个 hook，都不改 guest 代码：

| hook 点 | 语义 | 动作 |
|---|---|---|
| `+0x83190` | `FUN_00183190` 入口（每次构建一次） | 置 `tableNeedsZero = true` |
| `+0x832a0` | 每条记录的第一次取槽 | 若置位 → 清零 `(mask+1)*16` 字节，然后复位 |

```java
Hook arm  = new Hook(ctx -> tableNeedsZero = true);        // +0x83190
Hook zero = new Hook(ctx -> {                             // +0x832a0
    if (!tableNeedsZero) return;
    long table = reg(X20);                                 // 表基址
    long mask  = reg(X28);                                 // 容量-1
    tableNeedsZero = false;
    memWrite(table, new byte[(int) ((mask + 1) * 16)]);     // 插入之前清，且只清一次
});
```

> **为什么选 `+0x832a0` 而不是原来的 `+0x832b0`**：后者只在"该槽已被占用"时执行，
> 第 0 条记录若正好落在空槽就根本不会触发；前者是**每条记录的第一次取槽**，必然先执行。
> 这一个细节就是"清零可能发生在第 737 条"与"清零一定发生在第 0 条之前"的全部差别。

### 8.13.5 修复前后对照（同一 APK、同一 harness、同一份中央目录）

| 观测 | 修复前（run5） | 修复后（run6） |
|---|---|---|
| `zeroing ...` 记录条数 | 1（在构建中途） | **0** |
| 活跃槽位 / 可读名字 | 4,424 / 4,424 | **5,161 / 5,161** |
| `contains "assets/sign_verify.png"` | `false` | **`true`** |
| 闸门对目标资产的判定 | `lookup=0x0 -> absent` | **`lookup=0x3f7a -> present (not forced)`** |
| 31 次探针的判定分布 | 全部 absent | **10 present / 21 absent** |
| harness 路径替换（`WHITELIST-INPUT`） | 有（把目标名换成另一个真实条目） | **无** |
| `setkey` / `block_loop` 调用次数 | 0 / 0 | **2 / 7** |
| 目标 80 字节是否被读到 | 否 | **是**（`len=80`，`head=746db8cf…`） |

顺带把闸门本身也验证干净了：抽查 6 个 absent 的名字，其中 5 个在中央目录里
**确实不存在**（例如 `assets/images/cfg_xxx_hap_default.png`），
唯一真实存在的那个 `assets/images/icon_max_data_encrypted_xxxxxx.png` 判的是 present。

> **闸门不是白名单，它只是一个查表函数；表对了，它就对。**

**A/B 对照（同一个 harness，只改一个开关）**

```text
<prefix>.fixHashInit=false  → 1 次 zeroing、4,424 槽、sign_verify absent、setkey=0
<prefix>.fixHashInit=true   → 0 次 zeroing、5,161 槽、sign_verify present、setkey=2 / blocks=7
```

唯一变量就是这个开关，所以这把"相关"变成了"因果"。

顺带解释了一件旧事：关掉开关那一轮，harness 的"强制放行"
（`[WHITELIST-BYPASS] Forced match …`）确实把闸门的返回值改成了 1，
但 **`setkey` 仍然是 0**——因为闸门只负责"查表判存在"，
真正取数要的是**表里的句柄**；改返回值造不出一个合法句柄。
（反过来，把名字改写成**索引内真实存在**的条目就能跑通，这正是 [07 §7.10](07-SM4链路逐跳定位.md)
那个旁路对照当时成立的原因。）

### 8.13.7 四条教训（比结论更值得留）

1. **"运行观测"与"guest 行为"不是同一件事**，只要 harness 会往 guest 内存里写东西。
   我们自己的清零 hook 就是这样一个写入者——它写的那一下，被我们当成了"壳的索引不全"。
2. **静态事实的优先级更高，而且当时就已经报警了。**
   `FUN_00183190` "全量插入 / 任一非法即整体失败"这条事实，在 §8.12 就已经和"表里 4,424 条"冲突。
   我当时的推论是"所以构建者一定是别人"；正确的推论是"**所以这个观测不可能是真的**"。
   同一个矛盾，两种解读，差的是"更愿意怀疑代码还是更愿意怀疑仪器"。
3. **兜底逻辑必须有"合法路径不可能触发"的证明。**
   4,825 vs 200,000（41 倍）就是这个证明；缺了它，兜底就会变成一条"随机生效的正常路径"。
4. **"数字太干净"应当是警报，而不是结论。**
   缺口边界恰好落在一条记录的局部头偏移上、而不是页/段边界上；
   `5,161 − 4,424` 恰好等于被抹掉的前缀长度。这类完美形状，
   优先怀疑"观测方式"，其次才是"对方的设计"。
