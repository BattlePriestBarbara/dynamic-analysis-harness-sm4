# 01 样本与环境

## 1.1 样本形态

样本是**解包后的目录**（`<SAMPLE>`），不是 `.apk` 文件。这带来三点后果，必须在读任何结论前知道：

- 无法验证 APK Signature Scheme v2/v3 —— `APK Signing Block` 在解包时已丢失；
- 可完整读取 `classes*.dex`、`lib/`、`assets/`、`res/`、`resources.arsc`；
- `res/` 下的文件名已被**混淆改名**（4,107 个文件被扁平化为 `res/4uC.xml` 这类短随机名），
  因此 `META-INF/MANIFEST.MF` 里记录的条目名与磁盘文件名**对不上**——
  这条事实后来直接废掉了一条动态对抗路线（见 [04 §4.5](04-重打包与设备侧对抗.md)）。

`lib/` 下只有 `arm64-v8a` 一个 ABI，但 `assets/` 内仍带 `armeabi` / `armeabi-v7a` / `x86` / `x86_64`
四个 ABI 的风控 so 与加固运行时——即**主包单 ABI，插件多 ABI**。

## 1.4 三个环境层面的硬坑

这三个坑都不是"配置错误"，而是会**伪装成技术结论**的陷阱。

### 坑 1：非 ASCII 用户名把 classpath 拆坏

主机用户名含非 ASCII 字符，JVM 在把 `-cp` 传给 native 层时对路径编码处理不一致，
表现为**类找不到 / 依赖解析失败**，而错误信息完全指向"缺依赖"。

- 症状：`NoClassDefFoundError`，但 jar 明明在。
- 处置：把 classpath 写进 `cp.txt` 并以 `@cp.txt` 方式传入，或把工程放到纯 ASCII 路径下。
- 教训：**看到"缺依赖"先怀疑路径编码**，不要把时间花在补 jar 上。

### 坑 2：仿真器的调试器会在异常时阻塞

unidbg 的 `SimpleARM64Debugger` 在 guest 抛异常时会调用 `Scanner.nextLine()` 等交互输入。
在没有控制台的运行方式下（重定向 / CI），这会**永久阻塞**，外观和"卡死"完全一样。

- 处置：运行时重定向 stdin（例如从空文件读入）。
- 教训：**"挂住"和"失败"要分开验证**——先给 stdin 一个 EOF，再判断是不是真的死循环。

### 坑 3：Python 版本分裂

系统里同时存在多套 Python：一套是工具链自带（含 `numpy` / `scikit-learn` / `capstone` 的 native 侧），
另一套是系统 Python（缺这些包）。用错解释器会得到"包不存在"的假结论——本轮也因此
写出过一个**基于 capstone 的脚本却无法运行**（见 [12 §12.2](12-经验与教训.md)）。

- 处置：所有脚本以 `py -3.12` 显式调用，并在台账里记录解释器与包版本。
- 教训：**工具结论必须绑定环境**，否则"我这儿能跑"等于没跑。

## 1.5 为什么是这套组合

- **静态优先**：样本不可执行时（无设备），静态是唯一能给出确定结论的手段；且静态结论不依赖环境。
- **Ghidra 而非 IDA**：需要 headless + 自定义脚本批量改内存块权限，Ghidra 的脚本化成本更低。
- **unidbg 而非真机优先**：真机路线被"完整性校验 + 裸 syscall 退出"封死（[04](04-重打包与设备侧对抗.md)），
  仿真器能直接跳过启动期校验，且**天然可观测**（每次读写都能记账）。
- **自写解析器而非现成库**：`lief`、`androguard` 在这类刻意构造的畸形 ELF / 加密 DEX 上会失败或极慢，
  自写解析器反而更可靠，且能精确控制"只读我需要的字段"。

## 1.6 环境结论

> 本轮的**每一个结论都绑定了一个具体环境**：Ghidra 12.1.3、unidbg 0.9.10-SNAPSHOT、Python 3.12、
> Frida 17.18.0。换版本必须重跑关键测量，尤其是 ELF 解析与仿真初始化这两段——
> 它们对 linker 行为的建模差异很敏感。
