# 03 Ghidra 与"节头伪造"的代价

## 3.1 为什么必须上 Ghidra

`libexec.so` 的节头是假的（[02 §2.4](02-静态拆解.md)）。这意味着所有"信节头"的工具都会给出**一致但错误**的结论：

| 工具 | 看到的 | 真实 |
|---|---|---|
| `readelf -s` | 2 个导入符号 | 539 项哈希表 |
| IDA 自动分析 | 无 JNI、无导出，函数极少 | `JNI_OnLoad` 在 `0x72e74` |
| Ghidra 自动分析 | 大量重定位报错，代码区无法反汇编 | 代码区是**密文**，本来就不是代码 |

所以要做的不是"换个工具"，而是**先修工具的世界观**：让它按 `DT_HASH` 认符号、按 `PT_LOAD` 认段、
并强制把代码区当可执行块处理。

## 3.2 四次导入，逐步修正

| 轮次 | 动作 | 结果 | 结论 |
|---|---|---|---|
| 1 | 直接拖入 Ghidra 自动分析 | 刷屏 `Invalid symbol index (503)`；几乎无函数 | 节头不可信，必须换符号来源 |
| 2 | 写脚本按 `DT_HASH` 重建 539 个符号并 `createLabel` | 符号出现，但函数体仍无法反汇编 | 代码区不是代码，是密文 |
| 3 | 用自定义脚本把 `.text` 内存块强行标为可执行并播种入口 | 出现大量"函数"，但指令语义混乱（SVE 等） | **确认代码区是密文**：这是判据，不是失败 |
| 4 | 改为在**解密后的镜像**上分析（见 §3.5） | 一切正常 | 正确路线 |

> 第 3 轮是关键。它"看起来失败"，实际上是**证明了密文假设**——
> 如果代码区是可读代码，强制反汇编不可能出现成片的 SVE / 非法编码。

## 3.3 headless 命令原型

```powershell
analyzeHeadless.bat <GHIDRA_PROJ> <project> `
  -import <SAMPLE>/assets/ijm_lib/arm64-v8a/libexec.so `
  -postScript FixExec.java `
  -scriptPath <OUT>/ghidra_scripts
```

`FixExec.java` 做的三件事：

1. 读 `PT_LOAD`，把 RX 段的全部字节标为**可执行**（绕过 Ghidra 对"无节头区域"的处理）；
2. 从 `DT_INIT`、`e_entry`、`DT_INIT_ARRAY` 三处**播种**反汇编起点；
3. 对 `DT_HASH` 里的每个符号地址尝试 `createFunction`，失败则只建 label（不打断流程）。

## 3.4 Ghidra 给出的结论，以及它为什么到此为止

- 确认了 `INIT_ARRAY` 有 **70 个指针**（vaddr `0xF8680`，`0x230` B，全部 `R_AARCH64_RELATIVE`），
  去重后 **63 个不同函数**，其中 `0xE2D08` 被复用 **8 次**（疑似公共初始化例程）。
- 确认了 `DT_INIT = 0x985A0` 的 `DC CVAU` / `IC IVAU` 循环（[02 §2.4](02-静态拆解.md)）。
- **无法**给出 `JNI_OnLoad` 的语义——因为那些字节在磁盘上不是代码。

**到此为止的原因不是工具不行，而是输入不对。** 这是本轮最重要的方法论判断：
> 在一个"自我修改代码 + 伪造节头"的目标上，**静态工具的失败本身就是证据**，
> 它告诉你"这段数据不是它声称的东西"。

## 3.5 第二次用法：读解密后的镜像

unidbg 跑完初始化后，把整个映射区间 dump 出来（1,163,264 B，基址 `0x12000000`），
再以 `AARCH64:LE:64:v8A`、基址 `0x100000` 导入 Ghidra 才能正常反汇编。

**地址映射（必须记住）**：

```
image_addr = dump_addr − 0x12000000 + 0x100000
例：dump 0x82f48 → Ghidra 0x182f48
```

验证方式（不依赖任何假设）：

| 检查 | 做法 | 结果 |
|---|---|---|
| 偏移对得上 | `file_off 0x82f48` 是否等于 Ghidra `0x182f48` | ✓ |
| 序言对得上 | 该函数是否以 `x8 = 0x38`（`openat` 的 syscall 号）开头 | ✓ 与设备侧 `openat(AT_FDCWD=-0x64, …)` 的观测一致 |
| 全局对得上 | 镜像 `0x11c000` 是否等于 `spanFromElf()` 的重算值 | ✓ 逐字节相等 |

**一个反直觉但关键的发现**：**磁盘上的 `.so` 与镜像不是同一份代码。**

- 已发布的 `libexec.so`（sha256 `4fd13d12d64e6d45…`）在 `0x82f48 / 0x833e8 / 0x834e4 / 0x83af4 /
  0x556a4 / 0x73180 / 0x119710` 这些偏移上**不含**镜像里的字节；
- 只有镜像才有解密后的代码。

→ **所有静态分析必须以镜像为输入**；拿 `.so` 去核对地址只会得出"地址错"的假结论。

## 3.6 这一阶段的教训

1. **工具的一致性不等于正确性**：`readelf`、IDA、Ghidra 都信节头，所以它们"一致地错"。
2. **报错信息是证据**：`Invalid symbol index (503)` 同时证明了"节头只有 3 项"和"真实符号远超 3 项"。
3. **强制反汇编出现的乱码是判据**：成片 SVE / 非法编码 ⇒ 密文，而不是"架构识别错了"。
4. **地址必须绑定基址**：`0x120833e8`（镜像基址 `0x12000000`）与 `0x182f48`（Ghidra 基址 `0x100000`）
   指同一处——报告里凡出现地址，必须同时说明基址，否则无法复现。
