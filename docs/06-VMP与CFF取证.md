# 06 VMP 与 CFF 取证

## 6.1 为什么又回到静态

一期拿到镜像后，下一步自然是"在镜像里找解密器"。而 `IJMDal.Data`（1.37 MB 全随机）
一直是最大的嫌疑：它不像 DEX 容器，更像是**被加密的字节码或数据**。

于是问题被拆成两个，按顺序问：

1. **密文里到底有没有明文？**（如果藏了一个明文容器，就不必解密）
2. **哪个函数是解释器/解密器？**（52,529 个基本块里选一个）

## 6.2 问题一：`IJMDal.Data` 里没有明文（已被问死）

| 指标 | 实测 | 对照 |
|---|---|---|
| 全局熵 | **7.99986** | 8.0 = 完美随机 |
| 滑窗熵中位数 | **7.591** | 随机零假设 **7.5904 ± 0.0341**（z = **−0.52**） |
| 熵边界（1.37 MB 内） | **0 个** | — |
| ≥64 B 的零串 | **0 处** | — |
| ≥64 B 的可打印串 | **0 处** | — |
| JSON 形状命中 | 22 | 随机期望 **20.95** |

**结论**：`IJMDal.Data` 是单一均匀随机段，**在任何偏移上都没有藏明文容器**。
这个结论是"排除法"的核心——它让后续工作不必再猜"是不是藏了个 zip"。

> 注意 z = −0.52 的意义：滑窗熵**低于**完美随机一点点，且完全落在随机波动内。
> 如果里面有结构，滑窗熵会**显著**低于零假设。这里没有。

## 6.3 问题二：52,529 个块里挑一个

用块级特征排序（入度、回边、表加载密度、成员数），Top-1 是：

| 指标 | 值 |
|---|---|
| 块地址 | **`0x120bd8ac`**（文件偏移 `+0xbd8ac`） |
| 基本块数（n） | 13 |
| 成员密度（mem） | 0.92 |
| 入度（in_degree） | **96** |
| 回边（back_edges） | **96** |
| 表加载（table） | 1 |
| 索引加载比（idxld） | 0.077 |
| 置信度 | **1.000** |
| 96 个前驱跨度 | **27,692 B** |

96 个前驱恰好对应"变体栈偏移上测到的 96 个 `b` 站点"——两个独立信号在同一个数字上收敛。

**排序是否被"调过参"？** 用已知壳代码做 ground truth：它们排在第 **5,861 / 13,787 / 17,770** 位
（共 52,529）。**已知壳代码并不占据榜首** → 排名是诚实的，不是为答案量身定制的。

## 6.4 它是什么：96 块 CFF 状态机，不是 VMP ISA

这是本轮最有价值的**否定性结论**。四条独立证据：

### (1) 96 个前驱是**一个模板**，不是 96 个 handler

- 归一化后只有 **2 种形状**：95 个站点是 `and; orr; eor; eor`，1 个站点是同一条链
  但状态字节被重载进 `w10` 再移到 `w8`；
- **全 96 个站点共享 1 条掩码链**；
- **0 个链立即数**——没有任何站点携带 opcode 常量；
- 路径上的立即数只有 `#1`（步进计数）和 `0x3b`，而 `0x3b` 在 96 个站点上**全部是死代码**
  （`b .+8` 直接跳过 `mov w9,#0x3b`）；
- 分发索引**不是 vPC 字节**，而是 `ldrb w8,[sp,#0x82c]`——一个由前驱自己在两条指令前写入的栈字节。

### (2) 状态表可以被完整反解

- 表基址由 `adrp/add` 静态解析：`+0xbd74c` / `+0xbd750` → **`0x120f3af0`**；
- **256 项，256/256 全部落在镜像内**；**228 个不同目标**；**25 项指回枢纽本身**；
- 反解表后，**96/96 全部闭合**：`pred → state → target`，且映射是**双射**（96 前驱，96 个不同状态）；
- 每个状态都解析到 `pred + 4`，即**后继就是 fall-through**。

### (3) 语义因此是"goto next block"

一个把所有后继都指向 fall-through 的状态机，其**唯一语义**是"把直线代码打散成块再串起来"。
这正是**控制流平坦化（CFF）**的定义。它确实是"被分发的真实代码"，
但**没有属于自己的逐块语义**——所以不存在"opcode 表"可以提取。

### (4) 于是：这里没有 VMP ISA

> 把 96 个站点读成 handler、把 `0x3b` 读成 opcode，
> 得到的是**混淆器的形状**，而不是 **VM 的语义**。

## 6.5 一次撤回：`0x120f42f0` 不是表基址

早期版本曾把 `0x120f42f0` 当作 CFF 表基址。**这个前提已撤回**，原因是：

- 它没有任何 `adrp + add` 引用指向；
- 它恰好等于 `0x120f3af0 + 256 × 8`，即**已解析表区间的"末尾后一格"**。

更麻烦的是：把工具指向 `0x120f42f0` 时，它**仍然读出 256/256 项全在镜像内**——
这解释了为什么"所有指针都在镜像里"从来不是充分证据。

> **控制运行（control run）保留在产物里**：同一工具、同一镜像、旧基址，
> 输出 `_control_badbase.{json,csv,txt}`，与正确基址的输出并列存放。
> 这是"结论可被自己推翻"的具体实现。

## 6.6 另一个易踩的坑：751 个 qword 的指针游程

`0x120f3a50..0x120f51c8` 是一段 **751 个 qword 的指针数组**，
CFF 状态表只是其中**第 20 项**。这段游程**不属于控制流图，也不携带状态语义**。
把它当"更大的状态表"会把分析带偏。

## 6.7 可达性：哪些是活的

对照结果是本轮最反直觉的一条：

| 对象 | 状态 |
|---|---|
| `0x120bd8ac` 枢纽 | **活**（在初始化路径上被真实执行） |
| 96 个前驱 | 活（但只有"串接"语义） |
| `0x3b` 常量 | **死**（被 `b .+8` 跳过） |
| 25 个指回枢纽的表项 | 活（形成闭环展平） |

> "存在"不等于"被使用"。`0x3b` 是一个**被刻意放在死路径上的诱饵常量**——
> 它存在的唯一目的，就是让"挖 opcode"的人挖到一个看起来很像 opcode 的值。

## 6.8 这一章的结论

1. `IJMDal.Data` 不含明文（熵证据完整，无边界、无串、无结构）。
2. `0x120bd8ac` 是**控制流平坦化状态机**，不是 VMP 解释器。
3. 因此**通往明文的静态道路不是"解码 `+0xbd8ac` 的 VM ISA"**——
   真正的解密器，或消费 `IJMDal.Data` 的那个函数，**仍在镜像里且尚未定位**。
4. 这条否定性结论省下的工作量，远超它花掉的：任何"提取 opcode 表"的尝试都是白工。
